# D5O phase configuration prototype boundary

This document describes the prototype phase-form contract and its published source. The default templates remain in `components/d5o/platform/phase-configuration.ts`; authenticated System Administrators may copy them into a versioned `d5oPresentation.phaseContract` within the existing configuration-tenant version. The contract does not replace the M1 gate/authority graph or establish real delegated business authority.

## What configuration means

A configuration has a schema version, an exact Work Type key, a version, a named reference pack, six phase definitions, component definitions, and review rules. Each component declares its source and input kind. Structured registers declare their fields; a review rule is met only when at least one row exists and every required field in every row is complete. Labels and help text do not determine authority.

The current catalog contains Rybex Technical delivery and Lifecycle service, and Rotork Modernization service and Lifecycle service templates. A published contract is resolved through the selected workspace's one eligible configuration tenant and an exact Work Type match. New Discover captures pin the active published version ID. The shared Start Work form also lists only Work Types in the active published contract and sends its exact version to the authenticated local catalog API; that API rechecks the workspace version and Work Type before writing. The resolver loads the pinned published or superseded version for in-flight work and fails closed if that version or Work Type is unavailable. Existing browser records without a phase-form pin retain their legacy reference contract; they are not silently moved to the new active default.

Discover owns the estimate and proposal revisions. The capture drawer reads its available Work Types and source, procurement, customer-need, and date labels/options from the active phase contract. Its existing commercial workflow remains prototype-local. Define reads the selected Work Record's pinned phase contract, including structured register columns and `rows_complete` review rules. It records the estimate revision, proposal revision, Work Type key, and exact configuration version when requesting review. A changed commercial source requires a new definition revision; activating a later default alone does not invalidate work pinned to an earlier version. Prior review events remain in history. Legacy summary strings are derived for existing prototype views and are not an independent source of truth.

## Administrator and publication boundary

The Workspace configuration page shows the selected workspace's two reference packs and their six phases for inspection. It reads the actual configuration-tenant and version inventory through the authenticated server client. Resolution fails closed for zero or multiple mappings and for an unavailable active published version. The inventory distinguishes the tenant's active published version from reference layouts and identifies whether the current workspace membership has the single `admin` role used for System Administrator rights. Non-admin users do not see draft versions or publication controls; historical versions are behind a disclosure. Appearance, Work Type options, and synthetic commercial profiles remain browser-local prototype preferences, with visible edit controls limited to an authenticated `admin` membership. That UI restriction is not authoritative server enforcement over those local-only preferences.

The System Administrator panel creates a server-owned draft by copying the active version's populated M1 graph. The copy fails closed if the source contains version-scoped tables outside the verified graph. The administrator can edit the six presentation phase labels, Discover/Define component labels and guidance, and Define register field labels and required flags, and add typed text columns to those registers. Each `rows_complete` rule is kept aligned with the required columns. The protected fact paths, operators, comparison values, and review stage cannot be changed through this editor. A change reason is required. Draft save validates the phase contract; publication validates it again with the database manifest validator and validates the M1 graph in one database transaction. A separate activation changes the default for new work. Existing governed work keeps its exact pinned version. Audit events record creation, draft update, publication, and activation. Candidates use separate configuration branches because the database disallows overlapping published intervals within a branch.

The Workspace configuration preview reads the active published phase-form contract when available. The browser-local Discover/Define evaluator reads that same published contract for pinned work. Start Work's shared catalog is local prototype persistence; its version check does not turn that catalog into the M1 authoritative Work Record command. The M1 database gate and authority graph remains the only authoritative command contract. The phase editor does not edit arbitrary components, protected rule semantics, gate authority, or the full product lifecycle. The draft/publish/activate command is scoped to the owned disposable environment and is not production authorization. Browser-only appearance, older Work Type preferences outside the Start Work form, synthetic commercial role queues, and historical unpinned browser records remain separate prototype limitations.

Develop, Design, Deploy, and Operate have direct phase navigation on the same Work Record and in the main sidebar alongside Discover and Define. The sidebar selects an explicit Work Record before entering a record-scoped phase; its Work Hub and other workspace tools remain separate. Develop owns solution feasibility, Design owns controlled Work Packages and dated crew demand, Deploy owns execution and routes named bookings to Crew Schedule, and Operate owns receiving obligations and lifecycle follow-through. People & capacity is the shared resource reference across phases; it does not create bookings. The older Plan, Execution, and Handoff route names remain compatibility aliases for existing links and configured checks. Phase entries persist in the local shared prototype snapshot under the selected record's exact phase-form version. Their field labels, types, required-within-row flags, phase purpose, component labels, and guidance come from the pinned published contract. An older pinned version without those fields stays on its older form and does not silently inherit new fields. The System Administrator can revise supported field labels and required flags in a draft; new versions affect new work only.

The Design verification-plan package field is a controlled reference to a Work Package on the same Work Record. The interface renders a selector from the existing package register; saving rejects an unknown package ID. A record without packages must create one in Design first. Older prototype rows containing a typed package name remain visible as unlinked references until explicitly edited; they are not silently matched by name.

Newly published Rybex Technical delivery and Rotork Modernization service versions may also carry `decisionGuards`: keyed decision rights with typed checks over structured phase registers, linked Work Packages, package facts, reviewed proof references, and lifecycle actions. The same evaluator reads the Work Record's pinned version on the Work Record, Work hub, My work, and Decision queue. A missing pinned version or missing check binding for the current configured transition blocks the prototype decision. Completing one required input removes only its own blocker. Presentation-label changes do not change the check. A System Administrator may publish revised checks in a later configuration version; that does not change earlier pinned work. Older published form-only versions remain readable with their prior behavior. The configuration editor does not yet expose direct check editing; a bounded authored manifest and authenticated publish flow supplied the current synthetic reference checks.

For newly pinned records, Work Record Overview now presents the individual current decision checks and their satisfied/open status from that same evaluator, with a link to each owning surface. The Lifecycle surface presents those pinned checks for the next decision right and labels future positions as reference context. It sends previously recorded rights to History. Historical form-only records retain their earlier Overview. This prevents a hand-coded scenario milestone from claiming a different current verdict than the decision composer.

Plan, Execution, and Handoff phase panels now show only the pinned checks that belong to the current decision and that phase, including each check's met/open result. A check owned by another Work Record surface links there. The configured decision profile is shown separately from the Work Record's accountable owner; a synthetic profile is not proof that the signed-in person holds that right. On Plan, the phase with a current check appears first so the required action is visible without scrolling past unrelated context. These status panels read the shared evaluator; they do not create another gate or grant authority.

Other later-phase components lead to their existing operational controls: Work Packages and crew demand in Plan, facts in Execution, proof in Evidence, current gate review in Readiness, commercial context, lifecycle actions, and value. The phase panel keeps context without an immediate action in a disclosure rather than duplicating those systems. The configured forms are prototype-local inputs. They do not replace the M1 database-owned readiness/evidence/authority evaluator, confer decision authority, or release work. A missing pinned configuration disables the phase form and calls for restoration of that exact version.

The visible stage advance for newly pinned prototype Work Records follows the existing configured lifecycle transition right after the pinned decision checks clear. This stage and its history are saved in the local prototype snapshot. They are **not** the server-owned, atomic M1 authoritative command, and the browser-local snapshot API is not an authorization boundary. Package quantities, status, and Work Record lifecycle changes still require the planned server-owned implementation. The new checks improve prototype consistency and reviewability; they do not qualify production gate enforcement.

## Prototype acceptance checks

All six phase pages now use one Work Record page frame: back navigation, record identity and current position, the six-phase journey, the same Work Record controls, and a primary work column with a secondary action rail. Discover and Define keep their phase-specific pursuit and definition tools in the primary column and their record queues in the rail; workspace summary information follows the active work rather than leading the page. Queue selection and the sidebar Work Record selector stay aligned. A record without an eligible Discover pursuit or Define baseline causes an explicit fallback notice instead of opening unrelated detail under that selection.

`node scripts/qa-phase-configuration.mjs` checks the template structures and rule evaluator. `node scripts/qa-published-phase-contract.mjs` checks tenant isolation, published version selection, old pin preservation, configured decision checks for both tenants, label invariance, linked-package checks, malformed decision checks, structured later-phase fields, duplicate-schedule rejection, register requirements, protected commercial semantics, and fail-closed unavailable versions. `node scripts/qa-published-phase-contract-db.mjs` checks the forward-only database manifest validator. `node scripts/qa-phase-contract-activation.mjs` checks both disposable tenant defaults and old database pins. `node scripts/qa-shared-phase-pin.mjs` checks active-version creation, stale and incompatible rejection, and durable local-catalog reload for both tenants. The shared catalog regression checks cross-session package and schedule visibility. The prior configuration-publication transactional test established administrator publication, non-admin denial, and gate-graph pinning before the synthetic defaults were advanced. Typecheck, ESLint and a browser exercise of Develop, Design, Deploy and Operate cover the prototype UI and local snapshot persistence. These checks do not establish production readiness or real delegated commercial authority.
